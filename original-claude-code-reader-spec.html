BlindPilot — Original Claude Code Reader Build Specification

Historical source credit: BlindPilot is based on the original Claude Code Reader by doubletaponair. This document is retained to credit and describe that original Claude-only design. It is not the specification for BlindPilot's current multi-backend release.

This is a build specification for a small accessible desktop application that wraps the Claude Code CLI. The goal is to give a screen reader user (VoiceOver on Mac, NVDA or JAWS on Windows) a clean, keyboard-first interface for interacting with Claude Code, without the spinner animations, ANSI colour codes, and streaming text updates that make the standard terminal experience hostile to screen readers.

Project Goal

Build a single cross-platform Python application using PyQt6 that:

  • Accepts a user prompt via a text input field
  • Sends that prompt to Claude Code in headless mode
  • Captures the assistant's response cleanly, ignoring tool-use noise
  • Displays each response as one item in a navigable list
  • Allows the user to filter the list by typing in a search field
  • Maintains conversation continuity across multiple turns within a session

Target Platforms

  • macOS (current versions, tested with VoiceOver)
  • Windows 10 and 11 (tested with NVDA and JAWS)

One Python codebase should run on both platforms without modification.

Tech Stack

  • Python 3.10 or later
  • PyQt6 for the GUI
  • The standard library subprocess module for invoking Claude Code
  • The standard library json module for parsing stream output
  • No additional dependencies beyond PyQt6

The Claude Code CLI must already be installed on the user's machine. The app shells out to it; it does not bundle it.

Window Layout

A single main window with the following controls stacked vertically from top to bottom:

  1. Prompt input — A multi-line text field (QPlainTextEdit) where the user types their prompt to Claude. Accessible name: "Prompt". Approximately 4 lines tall by default; resizable.
  2. Send button — A standard push button (QPushButton) labelled "Send". Pressing Enter while focused on the prompt input should also trigger send (Shift+Enter inserts a newline within the prompt).
  3. Search field — A single-line text field (QLineEdit) labelled "Search responses". The user types a search term and presses Enter to filter the message list. Clearing the field and pressing Enter restores the full list.
  4. Message list — A list view (QListWidget) that displays each assistant response as a single list item. Accessible name: "Responses". This is where the user spends most of their time reading.
  5. Status bar — At the bottom of the window, a status line (QStatusBar) used to display state messages such as "Ready", "Sending...", "Receiving response...", "Error: Claude Code not found", and so on. Status bar text must be readable by screen readers when the user navigates to it.

Tab Order

Tab moves focus in this exact order, cycling at the end:

  1. Prompt input
  2. Send button
  3. Search field
  4. Message list

Shift+Tab reverses the order. The status bar is not in the tab cycle; it is read on demand by the screen reader.

Keyboard Behaviour

  • Enter in the prompt input sends the prompt. Shift+Enter inserts a newline.
  • Enter in the search field applies the filter to the message list. The list re-populates to show only matching items.
  • Up and Down arrows in the message list move between responses. The screen reader announces each response's text as focus moves.
  • Enter on a message list item opens that response in a separate read-only dialog (QDialog containing a QPlainTextEdit in read-only mode) for distraction-free reading. Escape closes the dialog and returns focus to the list.
  • Ctrl+L (Cmd+L on Mac) moves focus to the prompt input from anywhere in the app — a quick way to start a new prompt.
  • Ctrl+F (Cmd+F on Mac) moves focus to the search field.

Search Behaviour

  • Search filters the message list to only items whose response text contains the search term. It does not search prompts or metadata.
  • Search is case-insensitive.
  • Search is plain substring match — no regex, no wildcards, nothing clever.
  • Search activates only when Enter is pressed in the search field. Live filtering as the user types is explicitly not wanted, because list count changes are noisy with a screen reader.
  • Clearing the search field and pressing Enter restores the full list.
  • When the filter is applied, the status bar should update to read something like "Showing 3 of 12 responses".

Claude Code Integration

The app invokes Claude Code as a subprocess. The exact command pattern:

claude -p "<user prompt>" --output-format stream-json --verbose

For follow-up turns within the same conversation, capture the session_id from the first response and pass it on subsequent calls:

claude -p "<next prompt>" --resume <session_id> --output-format stream-json --verbose

The stream-json format produces newline-delimited JSON events on stdout. The app must read stdout line by line as the subprocess runs. Each line is a JSON object with a type field. The app should:

  • Parse each line as JSON
  • Keep events where type is "assistant" and the message contains text content
  • Concatenate text content blocks within a single assistant message into one string
  • Append that string as a new item to the message list when the assistant turn completes
  • Ignore events of type "user", "system", "tool_use", "tool_result", and any other type — these are the noise we are deliberately suppressing
  • Capture the session_id from the first "system" event (subtype "init") and store it for the lifetime of the session
  • Detect the final event of type "result" as the signal that the turn is complete

The subprocess call must run on a background thread (QThread) so the UI stays responsive. Use Qt signals to deliver new messages from the worker thread to the main thread, where they are added to the list widget.

Status and Feedback

The status bar should reflect the app's current state at all times:

  • "Ready" — when idle and no prompt is in progress
  • "Sending..." — immediately after the user presses Send
  • "Receiving response..." — once the first assistant event arrives
  • "Response received" — after the result event indicates completion
  • "Showing N of M responses" — when a search filter is active
  • "Error: <description>" — on any failure (see error handling below)

When a new response is added to the list, the app should also emit a QAccessible announcement so the screen reader can speak "New response received" without the user having to navigate to find out. On Windows this uses QAccessible.updateAccessibility with an alert event; on Mac VoiceOver picks up posted notifications similarly. The exact API may need testing on both platforms.

Error Handling

The app must handle these failure modes gracefully, with the error surfaced in the status bar and announced to the screen reader:

  • Claude Code CLI not found on PATH — show "Error: Claude Code not installed. Install from claude.com/claude-code"
  • Subprocess exits with non-zero status — show "Error: Claude Code exited with code N"
  • Malformed JSON on stdout — log it but do not crash; continue reading subsequent lines
  • Empty prompt submitted — show "Error: Prompt is empty" and do not invoke the CLI
  • No response received within a reasonable timeout (e.g. 5 minutes) — offer to cancel and show "Error: No response received"

Accessibility Requirements

These are not optional polish items; they are the reason the app exists.

  • Every interactive control must have a meaningful accessibleName set explicitly. Do not rely on automatic name inference from labels.
  • Every interactive control must have an accessibleDescription where the name alone is not self-explanatory.
  • The message list must use QListWidget (not a custom widget) so that the standard list role is exposed to screen readers. Each item's text is set via setText() only — no rich text or HTML in list items, because this complicates screen reader output.
  • Buttons must have visible text labels. No icon-only buttons.
  • Focus indicators must be visible (PyQt6's defaults are fine).
  • The window must support full keyboard operation. There must be no action that requires a mouse.
  • When the response viewer dialog opens, focus moves to the read-only text field automatically. When it closes, focus returns to the list item it was opened from.
  • The app should not steal focus when a new response arrives. The user may still be typing or reading. The screen reader announcement is sufficient notice.

Out of Scope for v1

To keep v1 small and shippable, deliberately exclude:

  • Saving or loading sessions to disk
  • Exporting responses to file
  • Multiple concurrent sessions or tabs
  • Settings or preferences dialog
  • Themes, fonts, or appearance customisation
  • Tool approval prompts (the app should run with default permissions; if a tool requires approval Claude Code will refuse it and the user will see that in the response)
  • Streaming partial responses into the list as they arrive (wait for the full assistant turn to complete before appending one list item)
  • Any kind of Markdown rendering — display the raw text from the response exactly as Claude returns it
  • Rich text, HTML, or syntax highlighting in the response viewer

File Structure

A single Python file is preferred for v1, named claude_reader.py. If the implementation needs to grow beyond roughly 600 lines, split into:

  • claude_reader.py — entry point and main window
  • worker.py — the QThread that runs the Claude Code subprocess
  • response_dialog.py — the read-only viewer dialog

Acceptance Criteria

The build is complete when all of the following are true:

  1. Running python claude_reader.py opens the main window on both Mac and Windows.
  2. Typing a prompt and pressing Enter sends it to Claude Code; the response appears as a new item in the message list within a reasonable time.
  3. Sending a follow-up prompt continues the same conversation (verified by referring back to earlier context, e.g. "what did I just ask you?").
  4. Tab moves focus through the four controls in the specified order.
  5. Up and Down arrows in the list cause VoiceOver (Mac) and NVDA (Windows) to read each response.
  6. Pressing Enter on a list item opens the response in a read-only dialog; Escape returns to the list.
  7. Typing a search term in the search field and pressing Enter filters the list to matching items only.
  8. The status bar reflects the app's state at all times.
  9. Killing the Claude Code subprocess (e.g. closing the window mid-response) does not leave orphan processes.
  10. No control is operable only by mouse.

Notes for the Builder

If you (Claude Code) are uncertain about any of these requirements, ask before guessing. The user is a blind developer who relies on this kind of tooling for daily work, so correctness on accessibility points matters more than speed of delivery. When in doubt, prefer the simpler, more standard PyQt6 widget over a custom solution — standard widgets get accessibility right by default; custom ones rarely do.
